PRODUCT VISION & OVERVIEW:
--------------------------------------------------------------------------------
ResolveAI (also known as ARRA - Autonomous Refund Resolution Agent) is an enterprise-
grade, production-ready web application designed to autonomously investigate, evaluate,
and resolve customer refund requests using deterministic decision rules, AI agent state
machine orchestration, human-in-the-loop escalation controls, robust audit logging,
and real-time operator analytics dashboards.

PHASE 1 — SYSTEM ARCHITECTURE & DATA FLOW
================================================================================

1.1 Data Flow Sequence
  1. Submission: Customer or external system POSTs a refund request to `/api/cases`.
  2. Case Creation: Backend creates DB record (`status="pending"`) and initializes ephemeral state store.
  3. Orchestration Trigger: Backend triggers the agent orchestrator state machine.
  4. Execution Loop:
     a. IdentifyProblem: Classifies refund request category (e.g., damaged, late_delivery, defective).
     b. GatherEvidence: Concurrently calls Order Lookup, Customer History, and Fraud Check tools.
     c. CheckPolicy: Searches policy rules based on category, amount, and order age.
     d. RecommendResolution: Runs pure deterministic decision engine with evidence snapshot.
     e. ExecuteOrEscalate:
        - If auto_approve: Calls Refund Creation tool. State becomes `auto_refunded`.
        - If auto_deny: Records denial rationale. State becomes `auto_denied`.
        - If escalate: Pushes to operator queue with priority tags. State becomes `escalated`.
  5. Operator Control: For escalated cases, human operator inspects full provenance timeline via dashboard and submits an approval/rejection action (`POST /api/cases/{id}/action`).

1.2 State Persistence Model
  - Short-Term Ephemeral Context: Redis hash (or thread-safe in-memory cache for dev) tracking visited states, evidence accumulator, tool retries, and decision draft.
  - Persistent Audit Ledger: PostgreSQL / SQLite database storing permanent case records, detailed step rationale, operator action logs, and tool invocation metadata.

PHASE 2 — AGENT DESIGN & STATE MACHINE ORCHESTRATION
================================================================================

2.1 State Machine Specification
  The orchestrator follows a strict deterministic finite state machine (FSM):
    [IdentifyProblem] ──> [GatherEvidence] ──> [CheckPolicy]
                                                     │
                                                     ▼
     [FinalOutcome] <── [ExecuteOrEscalate] <── [RecommendResolution]

2.2 Core Decision Logic (`decisions.py`)
  Decision rules enforce strict safety gates:
  - Fail-Safe Gate: If any critical tool call fails after 3 retries -> Force ESCALATE (`tool_failure`).
  - Fraud Risk Gate: If fraud score >= threshold (default 70) or fraud flags present -> Force ESCALATE (`fraud_risk`, rec: deny).
  - Abuse Rate Gate: If customer chargeback count > 0 or recent auto-refund limit exceeded -> Force ESCALATE (`abuse_suspected`).
  - High Value Gate: If refund amount > auto threshold (default $100.00 / 10,000 cents) -> Force ESCALATE (`high_value`). If amount >= dual-approval threshold ($500.00), tag `dual_approval_required`.
  - Policy Gate:
      * Verdict "allowed" & all gates passed -> AUTO-APPROVE (`approve_refund`).
      * Verdict "denied" & amount <= auto threshold -> AUTO-DENY (`deny`).
      * Verdict "conditional" or ambiguous -> ESCALATE (`policy_ambiguous`).

2.3 Visited State & Loop Detection
  - Visited states array tracks every state transition.
  - If any non-terminal state repeats more than max repeats (default 2), loop detector triggers `loop_detected_decision()` and immediately routes case to `ExecuteOrEscalate` with tag `loop_detected`.

PHASE 3 — TOOL CONNECTORS & RESILIENT WRAPPERS
================================================================================

3.1 Microservice Connectors
  - Order Lookup Tool (`order_lookup`): Fetches item details, order status, purchase timestamp, and order total.
  - Policy Search Tool (`policy_search`): Evaluates category rules, return windows, item eligibility, and verdict.
  - Customer History Tool (`customer_history`): Retrieves lifetime value, past refunds (90d), chargeback history, and dispute rate.
  - Fraud Check Tool (`fraud_check`): Computes risk score (0-100), velocity check, IP mismatch, and device signals.
  - Refund Creation Tool (`refund_creation`): Executes transaction with payment gateway, returns transaction ID.

3.2 Resilient Tool Wrapper (`tools/base.py`)
  - Automatic Retry & Backoff: Up to N (default 3) retries with configurable delay.
  - Structured Metadata: Every call returns `{ok: bool, data: dict, error: str, latency_ms: int}`.
  - Telemetry: Logs exact attempt number, latency, payload, and request ID into `ToolCall` database audit table.

PHASE 4 — BACKEND API & STATE PERSISTENCE IMPLEMENTATION
================================================================================

4.1 Key Endpoints
  - `POST /api/cases`: Create and execute a new refund investigation case.
  - `GET /api/cases`: Query cases with filtering by status (escalated, auto_refunded, etc.), tag, and search query.
  - `GET /api/cases/{id}`: Detailed case view including step timeline, tool logs, rationale, and events.
  - `POST /api/cases/{id}/action`: Operator action endpoint (approve, reject, request_info) with operator notes.
  - `POST /api/cases/{id}/replay`: Operator replay endpoint to re-trigger state machine investigation.
  - `GET /api/metrics/summary`: System metrics (autonomous resolution rate, avg latency, escalation breakdown).
  - `GET /health`: Health check endpoint.
  - `GET /metrics`: Prometheus raw metrics format endpoint.

4.2 Authentication & Security
  - Built-in JWT authentication & RBAC middleware supporting roles (`operator`, `admin`, `user`).
  - Protected API routes enforce bearer token validation.

PHASE 6 — SAFETY, HUMAN-IN-THE-LOOP & GOVERNANCE CONTROLS
================================================================================

6.1 Human-in-the-Loop Escalation Rules
  - All escalated cases require explicit operator authorization before refund creation.
  - Dual Approval Enforcement: Cases with refund amount >= $500 require approval from 2 separate operators before final execution.
  - Operator Audit Log: Every operator action records timestamp, operator username, role, action taken, and comment.

6.2 System Fail-Safe Rules
  - Tool Unavailability: If fraud or order service is down, system defaults to escalation rather than auto-approval.
  - Rate Limiting: Max auto-refund limit per customer within rolling window prevents abuse attacks.
